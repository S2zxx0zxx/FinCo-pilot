# Shared workspace deletion implementation — original #30

This implements the original #11 contract without changing archive into deletion. The separate `/workspace-deletion` center lists actual member workspaces, shows owner targets and supports archive, explicit collaborator resolution, consent, cancellation, saved-secret tracking and freshly authenticated operator review/execution/evidence. English and Hindi are separate. Global user accounts, personal authentication, subscriptions, payment evidence and other workspaces survive.

## Authorization and resolution

Only an actual owner member may request deletion; virtual manager, editor, viewer and superuser status alone are insufficient. A blocked request can be recorded. Execution requires an archived target, the requesting owner as the only member/owner and resolved payer, no other external manager, another accessible active workspace and no applicable verified hold. Historical record authors' account holds are also checked after membership exit. Ownership, identities, actual schema, holds, entire scoped graph and storage namespaces are checked again inside the PostgreSQL write fence. Review fingerprints expire after 24 hours; changes require re-review and invalidate evidence.

Existing member management remains explicit. Workspace row locks serialize membership/owner/archive changes and refresh authorization after waiting. Only active owners count towards the owner floor; removing an inactive co-owner does not falsely strand an active owner. The deletion screen requires the exact member UUID before remove/promote/demote. It does not remove the requester implicitly. Current uploader requests retain workspace KEY SHARE locks; an archive observed after waiting stops uploads.

A fresh actual requesting owner may detach the external manager via `POST /api/workspace-deletion/{request_id}/detach-manager`, body `confirmation` equal to the exact workspace UUID and `evidence_sha256` of actual protected evidence. The current actual payer-owner alone may transfer billing to the active requesting owner using the same body at `/{request_id}/transfer-billing`. An independent fresh superuser may repair a null payer at `/operator/{request_id}/repair-billing`, with real evidence and exact UUID. Repair cannot overwrite an existing payer. These actions create minimal hashed events and require an unstarted deletion request. They do not cancel subscriptions, refund payments or manufacture billing facts.

## Durable lifecycle and retention

Migration 100 adds workspace request, scoped hold and event tables while preserving existing rows. The ledger stores workspace UUID without a live workspace foreign key so a minimal tombstone survives deletion. One active request per workspace and an execution lease prevent duplicates/competing executors. A once-returned random receipt is hashed; status lookup uses `X-Deletion-Receipt` and no cookie/JWT/URL secret. Deletion APIs use no-store and sanitized SQL errors. Fresh full password/MFA/passkey or verified OIDC reauthentication is required for sensitive actions, reusing #29's freshness boundary.

A different current active operator performs execution. PostgreSQL EXCLUSIVE table fencing waits for writers/upload readers, then captures the exact inventory and commits primary purge plus durable retry manifest atomically. The #11 contract permits primary row deletion when safe durable object retry state is persisted; objects are not lost merely because their rows disappear. Reverse dependency deletion includes records written by former collaborators. Live MCP grants/arguments are removed; a bounded minimal aggregate hash/count security event is retained. User-level LLM keys, usage cost evidence and subscriptions are preserved; agent usage references detach via their existing SET NULL foreign keys. No workspace deletion silently revokes the user's unrelated provider connection or paid subscription.

Actual schema/table/column drift, unsafe storage references, inaccessible namespace inventories, shared object references and cross-workspace FK/self-reference/transfer edges fail closed before primary destruction. #29's exact namespace inventory, logo/invoice snapshot/orphan enumeration, local no-follow deletion and bounded S3 pagination are reused. Workspace-scoped bank connections require actual upstream revoke evidence before local deletion; processor inventory, verified holds/retention and backup inventory also require evidence.

Current byte deletion can be retried after crashes or outages. Storage provider/namespace changes block retries instead of deleting elsewhere. PostgreSQL guards reject scoped late writes and recreation of a deleted workspace UUID. The current deletion ledger must be applied before opening restored data. Existing backup restore quarantine stays in place; this change is not an automatic deletion-ledger replication or live restore approval service.

Post-primary processor copies, historical/unmapped legacy storage and S3 versions/multipart reconciliation need evidence after primary deletion. A normal S3 DELETE can leave recoverable versions, including historical namespaces with no visible current objects. The request remains `external_retry` until these steps are proven by operator attestations; it then enters `backup_expiry_pending`. Only real evidence of the earliest recoverable-data cutoff after primary cleanup and no later than now can complete the request. Scheduled dates alone cannot complete it. Exact file paths are removed from the ledger after reconciliation. Real evidence stays in the operator's protected evidence store; only hashes are submitted. These are attestations, not automatic provider confirmations.

Operators can add/release scoped holds through `POST /api/workspace-deletion/operator/holds` (`workspace_id`, reason code, evidence hash) and `/operator/holds/{hold_id}/release` (evidence hash), with fresh full authentication. Adding a hold after destruction starts is refused. Account deletion also checks private workspace holds and pending workspace requests so it cannot bypass these safeguards. Pending account deletion prevents a conflicting workspace workflow. Nonempty migration downgrade refuses to erase requests, hold or event evidence.

## Test and operational acceptance

Synthetic SQLite/API/UI tests cover owner-vs-manager authorization, archived/member/owner/manager/payer/last-workspace/hold blockers, changed inventories, duplicate requests, cancellation, receipt privacy, provider/storage retries with actual temporary bytes, mutual account-deletion gates, global subscription/account preservation and separate language interfaces. `scripts.verify_workspace_deletion_postgres` requires both CI=true and FINCO_DISPOSABLE_DB_TEST=yes, audits the actual full migrated schema, creates its own isolated synthetic schema, tests concurrent owner exits, actual scoped row/byte cleanup, global account/billing preservation, tombstone resurrection refusal and nonempty downgrade refusal. #29's native PostgreSQL stale-actor/upload/writer fencing tests remain in CI. Tests never destroy real user/production records.

Production execution requires PostgreSQL and a maintenance window; the bounded table-lock timeout fails closed. Live deployment, actual provider/processor/legacy storage/version cleanup and backup expiry require real operator evidence. No zero-vulnerability, legal-compliance, live-provider-erasure or backup-expiry certification is implied. Privacy/Terms remain transparent drafts; user deferred real publication/legal/operator facts until after #60. Paid billing gates remain shut.
