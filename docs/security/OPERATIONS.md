# Security operations, approvals and exception ledger

Engineering evidence owner: Codex during explicitly running tasks. Accountable human: founder/operator, name and deputy pending. Legal applicability/publication owner: qualified counsel plus operator, assignment pending. No claim of a staffed 24/7 department.

## Risk decisions

| Item | Classification | Current disposition | Close / review trigger |
|---|---|---|---|
| Import/AI/MCP diagnostic payload disclosure | Confirmed in isolated synthetic tests; confidentiality regression | Patched on branch; not deployed; no proof of a live breach | Exact-head CI, staging diagnostics and approved release |
| Main protection absent in API reads | Confirmed configuration observation | No owner risk acceptance assumed | Reviewed administration policy and effective enforcement proof |
| TLS min 1.0 / SSL full / permissive CSP | Confirmed zone/header observations | Production change withheld | Origin cert and client/provider tests plus owner release approval |
| Separate API subdomain unavailable | Confirmed public health observation | No inference apex login is broken | Identify canonical consumer and runtime configuration owner |
| Configurable outbound egress / import quotas | Suspected deployment-dependent risk | No exploitation, private-network probing or blanket change | Threat model, self-hosted compatibility and approved staged budgets |
| Secret candidates and remaining error surfaces | Unreviewed candidates, not confirmed secrets or leaks | Open triage; never declare clean based on regex alone | Redacted candidate review, private artifacts and runtime sample |
| Legal facts / external rights / restoration | External acceptance pending | No law-compliance or restore attestation | Owner/counsel facts, provider receipts, isolated native restore |

No exception is risk-accepted without a human owner, rationale, expiry and signature. Default review: next release or 30 days, whichever is earlier; confirmed critical incident escalates immediately. Keep sensitive incident details and real scanner material out of public issues.

## Monitoring budget and reporting

Use one security-specific daily change alert alongside existing performance/social tasks. GitHub maximum eight read-only API calls per run; up to three fixed public homepage/health GETs only when needed, no redirects outside the owned domains, no customer/auth/financial endpoints, no retries or load tests. Weekly review consolidates open risks, new routes/dependencies/advisories, test failures and legal changes. Use at most four primary-source legal/advisory lookups in a routine run. Do not auto-fix, merge or deploy from monitoring. Report only meaningful verified changes with timestamp, SHA, evidence, owner and next action; remain silent for unchanged known gaps. Actual automation creation/ID is recorded in checks.json; scheduling success does not prove subsequent delivery or continuous runtime coverage.

## Incident handling and clocks

Within the first hour: preserve private evidence with hashes and UTC/IST times; identify affected user/tenant/provider scope; nominate incident lead and counsel; recommend least disruptive containment. Never erase data, rotate production encryption keys, disable real authentication, send notices or post publicly without the applicable authorization. Confirmed active cross-tenant leakage/account takeover/payment bypass blocks release and immediately alerts owner.

Assess CERT-In coverage and Annexure I incident type immediately: directions specify six hours from noticing/being informed for covered entities/incidents, not six hours after completing forensics. Confirm PoC and current reporting method using the official directions. Check secure rolling ICT logs/India jurisdiction and clock synchronization requirements; source retention constants do not prove the actual log sink. GDPR/UK regulator and affected-person clocks depend on scope/risk; counsel owns that assessment. DPDP commencement and current rule requirements require fresh official verification; never reuse a generic 72-hour deadline for every incident or jurisdiction.

A tabletop packet must record discovery time, classification time, legal decision/time, responsible person, evidence store, containment/release decisions, notification approvals and recovery validation. No real incident or completed drill is claimed.

## Release and quarterly review

Before release: re-fetch main/overlapping PRs; verify exact candidate tree and checks, no migrations/data edits, independent review, known last-good artifact and reversible rollback. Test real provider signup/login/logout/reset/MFA, workspace read/write/export, payments, imports and AI tools on staging. Owner approves production promotion.

Quarterly: founder attests GitHub collaborators/rulesets, Cloudflare access/tokens, Vercel teams/env scopes, Neon grants/network paths, Sentry/support/SMTP/bank/payment access and dormant credentials; least privilege with removal decisions. Rehearse encrypted native backup restore and rollback; review processor regions/contracts, data rights/deletion tails and market/law applicability. Record signatures and evidence dates. No provider-access changes or actual signed quarterly review have occurred.
