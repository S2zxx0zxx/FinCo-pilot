# Roadmap #25 — encrypted backup and actual quarantined restore

## Scope and existing inventory

The app already exports selected workspace records as a JSON ZIP, optionally WinZip AES encrypted. That user download is not a disaster recovery backup: it excludes account authentication, many other database entities and raw attached files. The dialog now explains this distinction in English/Hindi without adding an unsafe public database-restore API. Export routes and tenant filtering remain unchanged.

This checkpoint adds operator-only `python -m scripts.disaster_recovery` commands and a real disposable PostgreSQL/Restic restore proof. The entire application database is captured, including migration versions, ownership/memberships, financial/payment/audit data, admin bootstrap closure and encrypted credentials. Referenced transaction/invoice attachments, current and issued-invoice logos, and locally stored knowledge documents are collected from that same database snapshot. Redis challenges/rate-limit state, reconstructible embedding model caches, environment files, provider credentials and private encryption keys are not put in the bundle.

## Architecture and tradeoffs

- PostgreSQL custom-format `pg_dump` uses an exported REPEATABLE READ snapshot shared with full table row counts/fingerprints and file-reference inventory. Canonical row serialization uses UTC, deterministic row order and length-delimited SHA256 hashing; all copied bytes have size/checksum metadata. The dump includes schema, constraints, indexes, sequences and all normal database data; roles/global server configuration are separately managed infrastructure. Table row fingerprints do not prove physical index layout, extension binary compatibility or continuous WAL recovery.
- Existing storage providers read immutable application keys. Missing/read-failed/mismatched referenced files abort backup instead of silently omitting data. Concurrent deletion between snapshot and file read can cause a visible failed backup; quiesce destructive jobs/writes for the first production rehearsal. Source keys must remain immutable. Independent manual object overwrites are outside this contract and must be prohibited by bucket permissions.
- Restic supplies authenticated client-side encryption, repository integrity and restore capabilities instead of inventing another encryption format. A completed private bundle is passed as stdin only after pg_dump/file collection succeed; no shell pipeline can mask producer failure. Nonzero/partial Restic exit codes do not count as successful backups. Backup success explicitly says **restore not proven**.
- Temporary plaintext stays in private directories; CLI umask 0077 and scheduler state directory/filesize limits apply. Use encrypted ephemeral staging storage with sufficient quota. Cleanup is not secure erasure and a killed process/host can leave private staging residue. Operator must reconcile residue after crashes; do not copy staging into another backup. Limits are 100,000 referenced files, 1 GiB per file and 100 GiB payload; tune/test deliberately for larger installations.
- `pg_dump` is a logical recovery checkpoint, not PITR/high availability. Managed physical snapshots/WAL/PITR should accompany it when the provider is selected. Initial operating targets: daily completed backup (nominal RPO <=24h) and rehearsed <=4h recovery target. Neither target is proven as a production SLA; delays/failures increase loss/exposure. Record measured restore duration and size before launch.

## Restore safety and release gates

Restore requires the **exact 64-character snapshot ID**, a fresh output directory, and `FINCO_RESTORE_DATABASE_URL` via secret environment/file, never a URI in command arguments. Target database name must be `finco_restore_<32 lower-case hex characters>`, must carry database comment `FINCO_ISOLATED_RESTORE_V1`, contain no user relations, and use a role without superuser/create-role/create-database/replication powers. Provision extensions with an administrator separately. Source and target database identities must differ; no `--clean`, overwrite, automatic database creation or production promotion command exists.

Before pg_restore, a persistent quarantine marker is committed. Restore checks the trusted encrypted bundle, rejects traversal/links/devices/duplicate/unknown members, validates every checksum and required credential decryption key ID, then runs pg_restore with exit-on-error, no owner/ACL/tablespace replay, and a single transaction. Every table count/content fingerprint and Alembic revision must match before post-restore security adjustments. Schema comes from a **trusted operator-owned** backup; PostgreSQL dumps can execute source-defined SQL and are never treated as untrusted user uploads.

After integrity verification, all user credential epochs rotate and external MCP inventory is revoked, preserving passwords, MFA and finance records. Knowledge paths are remapped into the fresh private recovery directory; object bytes are staged separately under `object-storage/`. They are **not uploaded into the original S3/R2 bucket or made live**. Populate and verify a separate recovery object namespace/bucket before cutover. Fresh isolated Redis must be used; never restore old challenges or connect restored workers to the original broker.

The canonical database-engine factory blocks restore database names, and its connection guard checks the persistent quarantine marker even after the database is renamed. API, MCP, workers and migrations use that factory. Restore orchestration alone has a narrow bypass to inspect its isolated target. There is no automatic release path. A failed operation leaves only the isolated target/output for operator diagnosis; it never repairs itself by altering the source.

Promotion remains blocked until an operator reviews current external deletion tombstones/legal holds, payment-provider reconciliation, encryption/key recovery, fresh Redis/worker/billing/SMTP boundaries and restored object storage. Earlier deletion work supplies policy/planning contracts, not an implemented durable deletion ledger; this checkpoint does **not** claim automatic tombstone replay. Do not release a historical backup merely because its tables match: it may resurrect later-deleted data or stale payment state. Any future release procedure must document applied ledger/hold/reconciliation evidence before setting the persistent marker's release decision and removing the isolated-name restriction through a deliberate infrastructure cutover. No release command is provided here.

## Keys, retention and operation

Preserve credential-encryption keys and compatibility key rings in a separate access-controlled recoverable secret store for the backup lifetime. The manifest contains only key identifiers, never keys; restore requires their availability. JWT/provider credentials are not archived. Provider/API secrets, configuration, pinned app release, extension/client versions, bucket configuration and separately backed-up bootstrap/operator controls belong in the recovery inventory. Lost Restic password or credential key ring can make retained data unusable; test separate-key recovery with authorised operators.

Commands from `backend/`, with PostgreSQL client 16+ compatible with the server and Restic installed (CI exercised Restic 0.16.4 and PostgreSQL16). Libpq uses the explicit DB CA file or system roots for verified TLS; system-root mode requires hostname verification, including when the app configured verify-ca. Test the provider hostname/CA and backup-specific DB timeouts with representative size before scheduling:

```sh
python -m scripts.disaster_recovery backup
python -m scripts.disaster_recovery check
python -m scripts.disaster_recovery expire
python -m scripts.disaster_recovery expire --apply
python -m scripts.disaster_recovery restore --snapshot <exact-id> --destination /private/new-recovery-directory
```

Configure `RESTIC_REPOSITORY`, a nonempty mode-0600 `RESTIC_PASSWORD_FILE`, scoped repository credentials and app settings/private secret files. Initial repository creation is an explicit operator action (`restic init`), never an automatic production fallback. Production requires an off-host S3 HTTPS/SFTP/REST HTTPS repository; insecure TLS override and ambiguous repository/password overrides are rejected. Prefer a dedicated backup repository in a separate failure/security domain, restricted read/write scope, and a separately secured recovery credential. R2 as the primary attachment store does not automatically mean its original bucket is a backup repository.

`expire` is dry-run by default. `--apply` selects only tagged FinCo snapshots at/beyond the absolute UTC 30-day maximum, forgets exact IDs, prunes unreachable data and checks repository structure. Selection is based on current time, not age relative to the newest backup; it does not retain an expired last snapshot. Unrelated tags/hosts are untouched. Legal holds require a separately approved controlled copy/repository, never an indefinite extension of every ordinary snapshot. A scheduler/network failure can delay physical deletion; monitor expiry/prune success and backlog. The code is a control implementation, **not proof that production expiry is active**.

`ops/backup/` contains separate daily backup/expiry and weekly full encrypted-read check systemd service/timer templates. Expiry is independent so failed backups do not indefinitely postpone deletion. Same-unit execution and CLI nonblocking lock avoid overlapping operations; Restic also locks repository mutation. Install only after replacing operator paths, setting a restricted OS identity, staging disk limits and secret files (including core signing/data keys; remove unused credential lines and provide other feature-specific secrets through the protected app environment/credential setup), verifying knowledge-storage mounts and setting failure alerting. Watch successful snapshot age, missing files, free space, restore duration, expiry/prune failure and full read checks; a timer being active is not recovery evidence. No timer is installed on a real host in this task.

## Actual engineering proof and remaining live acceptance

CI provisions random synthetic source/target databases and a restricted restore role; applies the **real full migration chain**, inserts financial precision/ownership/attachment/logo/knowledge/MFA/MCP records, writes real file bytes, runs pg_dump and Restic encryption, changes source data after capture, restores into the fresh target and compares **all** table fingerprints plus bytes. It verifies the original captured value, current source value unchanged, MFA decryption, epoch/MCP invalidation, wrong repository password rejection, ordinary-runtime quarantine including actual database rename, full repository read checks and real expiration/pruning of an old synthetic snapshot. Only CI-owned random databases/role/files are cleaned.

Local tests cover unsafe archive/key inputs, checksum/key-ring errors, exact retention boundaries including an expired last snapshot, credential permissions, ambient libpq redirection resistance, subprocess error privacy, production-target refusal and persistent quarantine. Existing export, storage, database, retention, auth and frontend suites remain part of final CI.

No VPS, production database, authorised offsite backup repository or real R2 bucket is supplied. Live acceptance remains pending: initialise an authorised private off-host repository, provision least-privilege backup/restore identities and separate key escrow, run the first representative backup/restore with version-compatible extensions and real object bytes in an isolated recovery namespace, record measured RPO/RTO, verify real scheduler/alerts/30-day expiry, apply fresh deletion/hold/payment reconciliation and confirm gated cutover. Synthetic CI cannot establish a real production recovery point or SLA. Next original roadmap item is #26; inspect its exact canonical scope before starting.
